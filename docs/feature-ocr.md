# 機能追加: 画像認識による素点入力(Cloud Vision API)

本ファイルは既存アプリへの**追加機能**の仕様。既存の `spec.md` / `page2.md` を前提とし、差分のみを記述する。

## 1. 目的

全自動麻雀卓(例: AMOS REXX III)の点数表示部をiPhoneで撮影し、Cloud Vision APIのOCRで4人の素点を読み取って、2ページ目の素点入力欄に自動セットする。手入力の手間を省くのが狙い。

## 2. 全体方針

- OCRはGAS経由でCloud Vision APIを呼び出す(フロントから直接は呼ばない)
- APIキーをGAS側に隠蔽できるため、publicリポジトリでも安全
- フロントは画像をbase64化してGASにPOST、結果(4つの数字)を受け取って素点欄にセット
- 認識結果はあくまで入力補助。ユーザーが確認・修正してから得点確定する

## 3. 事前準備(一度だけ)

### Google Cloud側

1. Google Cloudプロジェクトで Cloud Vision API を有効化
2. APIキーを発行(または既存のサービスアカウントを利用)
3. 必要なら請求アラートを設定(無料枠は機能ごと月1,000リクエスト)

### GAS側

- APIキーは**スクリプトプロパティ**に保存する(コード直書きを避ける)
  - `PropertiesService.getScriptProperties().getProperty('VISION_API_KEY')` で取得
  - 設定は一度だけ。GASエディタの「プロジェクトの設定 > スクリプト プロパティ」から登録
- コードにハードコードしてもGASソースは外部から見えないため実害はないが、プロパティ管理を推奨

## 4. 撮影・前処理(フロント)

- 「画像から入力」ボタンで**カメラを起動**する
  - `<input type="file" accept="image/*" capture="environment">` を使用(背面カメラ起動)
- 撮影後、送信前にCanvasでリサイズ・圧縮:
  - 長辺1280px程度に縮小
  - JPEG品質0.8程度で再エンコード
  - 目標: base64化後も1MB以下(Vision APIのJSON上限10MBに対し余裕を持たせる)
- 圧縮後の画像をbase64化してGASへ送信
- **圧縮後の画像はダイアログ表示にも使う**ため、フロント側で保持しておく(プルダウンを重ねる背景画像になる)

## 5. GAS API追加アクション

### `action: 'ocr'` - 画像から素点を読み取る

リクエスト:
```json
{
  "action": "ocr",
  "password": "...",
  "image": "<base64エンコードされたJPEG(プレフィックスなし)>"
}
```

レスポンス(成功):
```json
{
  "ok": true,
  "results": [
    { "score": 25000, "raw": "0250", "box": { "x": 0.18, "y": 0.30 } },
    { "score": 32400, "raw": "0324", "box": { "x": 0.62, "y": 0.30 } },
    { "score": 18600, "raw": "0186", "box": { "x": 0.40, "y": 0.55 } },
    { "score": 24000, "raw": "0240", "box": { "x": 0.78, "y": 0.62 } }
  ]
}
```

- `results`: 読み取った数字ごとに `score`(×100した実点数)、`raw`(生文字列)、`box`(画像内の相対座標 0〜1)を持つ配列
- `box` はダイアログでプルダウンを重ねる位置に使う(画像サイズに対する割合で返すと、フロントのリサイズに依存しない)
- 読み取れなかった箇所は `score` を `null`、`raw` を読めた範囲の文字列にする

### GAS処理の流れ

1. パスワード認証(既存の共通処理)
2. スクリプトプロパティからAPIキーを取得
3. Cloud Vision APIの `DOCUMENT_TEXT_DETECTION` または `TEXT_DETECTION` を呼び出し
   - 7セグLED表示なので、まず `TEXT_DETECTION` で試す
4. 返ってきたテキスト + バウンディングボックス座標から4つの数字を抽出
5. 各数字を ×100 して実点数化
6. 各数字の座標を画像サイズに対する相対値(0〜1)に変換
7. `results` 配列(score / raw / box)としてJSONで返却

> **責務の範囲**: GASは「4つの数字とその座標を返す」までが責務。どの数字がどのプレイヤーか、topをどう扱うかは**フロント側**で判断する。

## 6. プレイヤー位置のマッピング

- 全自動卓の表示部は4箇所に分かれて点数が出る(各プレイヤーの手前方向)
- GASはOCR結果のバウンディングボックスから各数字の**相対座標(0〜1)** を算出し、`results` の `box` として返す
- フロントはこの座標を使って、撮影画像の上の対応する位置にプルダウンを重ねて表示する
- 席順は対局ごとに変わるため、どの数字がどのプレイヤーかの最終確定は**ダイアログでユーザーが選択**する(セクション7参照)
- GASは「数字と座標を返す」までが責務。誰がどの席かは判断しない

> 注: 卓のモデルや撮影角度で座標が変わっても、ユーザーがダイアログで選び直せるので致命的にはならない。

## 7. フロントUI追加(2ページ目)

`page2.md` の素点入力エリアに以下を追加。

### ボタン

- **「画像から入力」ボタン**: 素点入力テーブルの近くに配置
  - タップで `<input type="file" capture>` を起動

### 処理フロー

1. 「画像から入力」ボタンタップ → カメラ起動
2. 撮影
3. 画像をCanvasで圧縮 → base64化
4. ローディング表示(「読み取り中...」)
5. GASに `action: 'ocr'` でPOST
6. レスポンスの `scores`(4人分)と各値の座標(バウンディングボックス)を受け取る
7. **割り当てダイアログを表示**(下記参照): 撮影画像を背景に表示し、読み取った4箇所の数字の近くにプレイヤー選択プルダウンを重ねて配置
8. ユーザーが各数字にプレイヤーを割り当て、重複がなければ右下のOKボタンが有効化
9. OK押下で2ページ目の素点入力欄に反映:
   - 割り当てに従って各プレイヤーの素点欄にセット
   - ただし **top(素点が最大の人)の欄は空欄**にする
   - `null`(読み取り失敗)の値もそのまま空欄
10. セット後、既存の自動計算ロジックが走る:
    - 空欄が1つ(=topの欄)だけなら、`100000 - 他3人の合計` でtopの素点が自動算出される
    - 続けて五捨六入→ウマ→勝点が自動計算される
11. ユーザーが値を確認・修正して「得点確定」

> **topを空欄にする理由**: 既存の得点計算は「1位の勝点を2〜4位から逆算して端数を1位に寄せる」思想。素点も同様に、topをOCRに頼らず他3人から逆算する方が、OCRの読み取り誤差をtopが吸収でき、4人の合計が必ず100000になる整合性も保てる。

> **読み取り失敗が複数ある場合**: top以外にも `null` があると空欄が2つ以上になり、自動計算は走らない(既存仕様どおり)。この場合ユーザーが手入力で空欄を1つにすれば、残りが自動計算される。

### 割り当てダイアログ

席順は対局ごとに変わりうるため、OCR後にどの数字がどのプレイヤーかを確定させるダイアログを表示する。

#### 構成

- **撮影した画像を背景に全面表示**するダイアログ(モーダル)
- 読み取った4箇所の数字それぞれの**近く(座標位置)にプレイヤー選択プルダウンを重ねて配置**
  - 座標はOCRレスポンスのバウンディングボックスから算出
  - プルダウンの選択肢は1ページ目で登録した4人
  - **初期値は前回の割り当て**(`lastAssignment`、初回は位置順にプレイヤー1〜4)
- **OKボタン**: ダイアログ右下に固定配置
  - 4人が重複なく割り当てられている時のみ有効
  - 同じプレイヤーが2箇所以上で選ばれている間は無効(重複箇所を赤表示で示す)
  - 押すと2ページ目に反映
- **キャンセル**: **ダイアログの外側(背景オーバーレイ)をタップ**すると閉じる
  - 割り当てを破棄して2ページ目に戻る(素点欄は変更しない)

#### レイアウトイメージ

```
┌────────────────────────────┐
│  ┌──────────────────────┐  │ ← 背景は撮影画像
│  │ [P1▼]25,000  [P2▼]32,400│ │
│  │                      │  │
│  │   [P3▼]18,600        │  │ ← 各数字の近くにプルダウン
│  │          [P4▼]24,000 │  │
│  │                      │  │
│  │              [  OK  ] │  │ ← 右下固定、重複なしで有効
│  └──────────────────────┘  │
│   (外側タップでキャンセル)   │
└────────────────────────────┘
```

#### 前回値の保持

- 割り当て(位置→プレイヤーの対応)を `lastAssignment` としてstateに保持
- 次回のOCR時に初期値として使う
- localStorageにも保存(24時間内なら次の局でも引き継ぐ)

### 認識結果の確認・修正

- 反映後の素点は通常の入力欄と同じく**編集可能**
- 読み取り誤差があればいつでも手修正できる
- 認識に失敗した欄(null)は空欄なので、既存の「空欄1つで自動計算」ロジックとも自然に整合する

### エラー処理

- OCR失敗(画像が不鮮明など)→ 共通エラー表示エリアに「読み取れませんでした。手入力してください」
- 通信失敗 → 「通信に失敗しました」、リトライ可能に
- いずれの場合も手入力にフォールバックできる

## 8. state への影響

- OCR結果(素点)自体は素点欄に流し込むだけで、永続的な保存は不要
- ただし**席順割り当ての前回値**を保持するため、stateに `lastAssignment` を追加する:

```js
{
  // ...既存state
  lastAssignment: [0, 1, 2, 3],  // results配列の順番に対応するプレイヤーindex
                                 // 初回は [0,1,2,3]、以降は前回の割り当てを保持
}
```

- `lastAssignment` はlocalStorageに保存(24時間内は次の局でも初期値として引き継ぐ)
- スプレッドには保存不要(アプリ内部の利便性のためだけのデータ)
- 素点(raw)はそもそもlocalStorage/スプレッドに保存しない方針のため、OCR結果も一時的に入力欄に表示されるだけ

## 9. コスト・制限の補足

- Cloud Vision API無料枠: 機能ごと月1,000リクエスト(無期限)
- 1局1回の撮影なら、毎日打っても無料枠に収まる規模
- 画像はJSONリクエスト全体で10MB以内(base64は元の約1.37倍になるので、圧縮して1MB以下推奨)

## 10. 段階的な実装の推奨

1. まずGASに `action: 'ocr'` を実装し、固定画像で4つの数字が取れることを確認
2. 座標マッピングのロジックを、実際の卓のサンプル画像で調整
3. フロントに「画像から入力」ボタンと圧縮処理を追加
4. 認識精度が不足する場合は前処理(二値化、LED色域抽出など)を検討
